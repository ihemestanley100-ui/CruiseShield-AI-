====================================================================== 1.
PRODUCT THESIS AND SIGNATURE EXPERIENCE
======================================================================

PROBLEM Transaction-by-transaction monitoring can miss suspicious
relationships spread across accounts, devices, phones, merchants,
beneficiaries, channels and time. Investigators need a traceable way to
understand why an event was flagged and what the surrounding network
actually shows.

SOLUTION CruiseShield AI turns a synthetic transaction into a connected,
evidence-linked investigation. A deterministic event/graph/rules
pipeline identifies seeded relationships and risk signals. Meta Muse
Spark explains the supplied evidence. Replay and a bounded what-if
simulation support analysis. A human decision gate records the
investigator’s choice, and an audit trail records the workflow.

CORE PROMISE “Move from a suspicious transaction to an explainable
network investigation in one controlled workflow.”

SIGNATURE SCENARIO - Transaction ID: txn_84721 - Display label:
Transaction #84721 - Amount: NGN 480,000 (display ₦480,000) - Sender:
Account A (acct_A) - Receiver: Account B (acct_B) - Seeded network
target: 12 accounts, 4 devices, 3 phones, 2 merchants, 1 beneficiary -
Source: synthetic_demo - Every record must be seeded synthetic data, not
a claim about real financial activity. - Reset must reproduce the same
scenario and expected relationships. - Graph expansion must be based on
seeded relationships and implemented logic. - Risk changes must be
calculated from graph/rule inputs, not triggered by a UI button alone.

REQUIRED USER JOURNEY DETECT → CONNECT → INVESTIGATE → EXPLAIN →
REPLAY/SIMULATE → HUMAN DECISION → CASE → AUDIT.

DEMO ACCEPTANCE A judge can start/reset the scenario, open transaction
#84721, reveal the real seeded graph, inspect an edge’s provenance, see
computed risk reasons, trigger an actual Meta Model API call, review
validated model findings, replay events, run a hypothetical simulation,
record a human decision with a reason, and inspect the resulting
case/audit history.

4. ARCHITECTURE AND TECHNICAL BOUNDARIES
======================================================================

VERTICAL SLICE Synthetic Event → Event Gateway → Validate / Normalize /
Idempotency → Entity Resolution → Feature Extraction → Rules Engine →
Graph Update / Network Features → Risk Assessment → Alert /
Investigation → Evidence Package → Meta Muse Spark Adapter → Schema and
Evidence Reference Validator → Investigation Studio → Replay / What-if
Simulation → Human Decision Gate → Case State → Audit Flight Recorder

BOUNDARIES - Domain services compute authoritative facts. - Database
persists canonical records. - Graph engine creates relationships only
from seeded/authorized data and deterministic logic. - Rules/risk engine
computes risk with versioned inputs and transparent contributions. -
Evidence service builds a bounded package with source references. - Meta
adapter calls the external model server-side. - Validator checks
response structure and evidence IDs. - Frontend renders API responses;
it must not manufacture facts or telemetry. - Human-decision service
validates allowed transitions and required reason. - Audit service
records relevant state changes and trace IDs.

STACK POLICY Inspect and reuse the existing stack. Do not migrate
frameworks just for preference. If a component is genuinely missing,
choose the smallest compatible option: - Frontend: existing framework;
Next.js + TypeScript only if a new app is needed. - UI: existing
component system; Tailwind if already compatible. - Backend: existing
API; compact server routes or existing FastAPI if already in use. -
Validation: existing schema library; Zod for TypeScript or Pydantic for
Python. - Storage: existing database; otherwise the simplest durable
option already supported. - Graph: typed node/edge records and
deterministic graph functions for MVP. - Model client: SDK pattern
documented by Meta, configured server-side. - Tests: existing runner
plus browser end-to-end test. - Deployment: existing hosting provider
and server-side secret store.

Do not add Redis, Kafka, Kubernetes, a vector database or a separate
graph database unless a concrete acceptance criterion requires it and
the current stack cannot meet it.

7. GRAPH, RULES AND RISK
======================================================================

Implement deterministic, versioned rules. Suitable rule families: -
amount threshold; - velocity within a defined time window; - device
reused across accounts; - phone reused across accounts; - beneficiary
concentration; - graph fan-in/fan-out; - multiple independent signals
linked to the same network; - channel-specific rule only when supported
by seeded facts.

Each rule definition must have rule ID/version, description, inputs,
threshold, severity, reason template, test cases and enabled state.

The score must: - use a documented deterministic function; - use
versioned weights/configuration; - stay within a documented range; -
expose contributions and input features; - have boundary and no-signal
tests; - recompute from actual rule/graph outputs; - never increase
merely because the Reveal Network button was clicked.

If no trained/calibrated model exists, label it “Deterministic demo risk
score,” not “fraud probability.”

“WHY THIS RISK?” must show: 1. rule/signal name; 2. observed value; 3.
threshold/comparison; 4. source event/entity/edge; 5. evidence ID; 6.
contribution to score, if implemented; 7. caveat: a risk signal is not
proof of criminal intent.

Graph interaction: - render graph data returned from backend; -
selecting a node reveals node details and evidence; - selecting an edge
reveals relationship, provenance and source event; - provide a
keyboard-accessible table/list alternative; - use a legend and readable
labels; - do not fabricate edges for visual density.

12. REPLAY, SIMULATION, CASES AND AUDIT
======================================================================

REPLAY - use deterministic ordered events; - show current replay cursor
and event timestamp; - show graph/edge changes and risk recomputation; -
support reset, step, play/pause; - same scenario version must reproduce
expected replay.

WHAT-IF SIMULATION - implement one bounded scenario, such as
removing/ignoring a selected seeded relationship and recomputing
graph-derived risk contribution; - clearly label the changed
assumption; - do not mutate baseline data; - save simulation inputs,
rule/code version, output, limitations and trace ID; - do not call it a
prediction of actual future crime.

CASE STATES NEW → TRIAGED → INVESTIGATING → AWAITING_REVIEW → DECISIONED
→ ACTIONED → CLOSED. Allow explicit alternatives such as FALSE_POSITIVE,
NO_ACTION and ESCALATED when valid. Validate transitions; reject invalid
transitions.

AUDIT Record: - scenario start/reset; - event processing; - graph/risk
calculation version; - evidence package generation; - AI request
metadata and validation; - simulation run; - human decision and
reason; - case transition; - failures/retries when relevant.

Audit events must be append-only at application level. Do not claim
tamper-proof audit unless cryptographic integrity protection is actually
implemented and tested.
